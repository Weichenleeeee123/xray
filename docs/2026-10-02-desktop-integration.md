# 桌面调研与恢复链路交接

本次已纳入主线至 `811ed1b`，包含队友的统一 FastAPI 首页部署、后端审计修复、双输入框恢复、示例选择和最新动作跟随。时钟的环节百分比与队友的阶段面板合并为同一个进度函数，避免函数重名及展示口径分叉。没有改动模型配置、证据抽取、引用/数字核对或确定性风险判定，也没有接入新的金额、替谁判断入口或修改报告视觉。

## 本次增加

- 主桌电脑显示公司全称，放在屏幕上沿以避开坐姿角色头部。超过屏幕宽度的名称缓慢往返显示，悬停/键盘聚焦可读取全称；随场景按比例缩放。
- 墙上时钟显示实际处理环节的完成比例。分母为后端计划的步骤数加一次案卷读回确认；收到完成事件但未校验保存时不显示 100%。失败、未查询仍保留原覆盖状态，不把百分比当作可靠性评分。
- 把社会舆情标签从时钟上移开；门口敲门提示与动作控制器统一接受 opinion/reviews 的真实 found 事件。角色映射复用队友实现，暂停、倍速只作用于动画。
- 原始请求完整保存在运行目录的 `*.input.json`，与进度日志分开、原子写入，不把合同正文放到 URL。首次读任务时恢复完整输入，增量查询不重复发送材料。补充任务也保留原案卷编号与完整补充内容。
- 断线“继续查看本次查询”只 GET 原任务；明确“重新查询”才 POST，携带原需求、材料和其他已有字段。旧任务没有完整输入时要求回首页确认，不能静默换成默认需求。
- 完成时校验任务编号、案卷编号及版本；保存确认失败只重新读案卷。保留主线已有的幂等请求键、并发控制、租约、冲突检测。
- 正式部署首选 `build:home` 后 FastAPI 单服务同源提供全部页面。可选的独立 Worker 部署增加实际转发入口，原路径转发 API、报告、图片与离线演示；请求体、上传文件、状态码和流式响应不被转换或截断。
- 报告/案卷/首页继续同标签导航；`/xray/#/new` 保留原完整材料表单，不被首页重定向误伤。

## 运行

默认方案见 README：在 research-room 执行 `npm run build:home`，然后启动 backend 的 FastAPI。首页、报告和 API 同端口。

独立 Worker 仅为可选方案：设置服务端 `XRAY_BACKEND_URL`，在 research-room 执行 `npm run build` 后再运行 `npm start`。Windows 上重新构建前停止旧的预览进程，否则它可能锁住 dist；不需要删除源文件或改权限。

模型/企查查密钥仍只在后端环境中配置，不放入前端变量或提交到 Git。

## 新材料二次分析：建议的下一步（本次未改报告界面）

下一步优先做“新材料改变了什么”，不增加另一份大报告：

1. 先给变化摘要，分类使用已有 `changes.kind`：新增疑点、加重、澄清、事实更新、证据不足、未变化。查不到旧记录不能显示为风险减轻。
2. 每个变化并排显示旧判断/旧依据、新判断/新依据，并列出这次新增材料标题、原文、时间和对应版本；已有 `before/after/because/quote` 可作为接口基础。
3. 原来的关注项保持可追溯；没有被新材料影响的项明确写“未变化”，避免用户误以为整份报告被推翻。
4. 付款主体改变等情况表达为“与已确认信息不一致，关系待核实”，附具体核实问题，不直接判定安全或诈骗。
5. 对外部来源刷新带来的变化，与用户新增材料带来的变化分开说明；证据指向不够细时先补后端出处，不能让模型编造因果解释。
6. 补充任务优先复用现有 `/api/cases/{id}/runs`、版本号和幂等机制，让新材料分析也能刷新恢复。前端展示仍交由报告负责人协作，不在这次桌面修改中抢改。
