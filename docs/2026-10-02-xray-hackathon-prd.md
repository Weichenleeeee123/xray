# X-Ray 黑客松版 PRD（48H 施工单）

- 日期：2026-10-02　版本：H1
- 施工以本文为准。[旧版 PRD](2026-10-02-xray-prd.md) 和三份交接文档只当原则参考，冲突时以本文为准。

## 0 一句话

在你把钱或信任交给一家公司之前，X-Ray 把它的宣传和它的记录摆在一起看：哪里对得上、哪里对不上、还缺什么、下一步该问什么，最后整理成一页家人看得懂的纸。

## 1 贴题对照

赛题（杭州银行「X-Ray | 透视·真相」）里的每个关键词，都要能指到一个功能上。

| 赛题原话 | 我们怎么回答 | 落在哪个功能 |
| --- | --- | --- |
| 家人和朋友把储蓄、信任交给一家公司 | 用户替家人查；主演示用储蓄理财案例；最后交付给家人的一页 | 建案卷里的"替谁看"、一页纸 |
| 你凭什么判断它靠得住 | 不靠感觉，也不靠 AI 打分：把它的说法和官方记录逐条对照 | 宣称 vs 记录 |
| 即将接手一家公司，看懂财务、识别风险 | "接手/入股"场景；从登记和年报里找财务压力的迹象 | 场景模板、财务信号 |
| 财务、信用、风险、口碑 | 四张信号卡，名字照抄赛题 | 四个信号 |
| 散在各处的线索 | 监管名单、公示记录、年报、处罚、投诉、用户材料汇进一个案卷，每条标来源和日期 | 数据来源 |
| 人人可懂 | 每条结论一句人话，术语点开有解释，给家人一页、给柜员一页 | 解释层、一页纸 |
| 从金融视角出发 | 第一问永远是"它有没有资格收这笔钱"，每条规则写明法规出处 | 资格核验、规则库 |

## 2 一条主线（所有场景共用）

和现有 [demo](../demo/index.html) 的六步一一对应：

1. **建案卷**：公司名、替谁看、交出去的是什么（即场景）、金额、最担心什么，再加上材料（宣传单、合同、聊天截图或文字）。
2. **透视宣传**：从材料里找出对方的说法，每条附原文。
3. **宣称 vs 记录**：每条说法对照记录，判定为以下六种之一（和现有代码一致）：与记录不符、不合规承诺、说法有误导、需要留意、无法核验、与记录相符。材料里"该有却没写"的内容（例如理财风险提示语）单独列一张清单。
4. **四个信号**：财务、信用、风险、口碑，每张卡一句人话，再列出带来源的明细。
5. **新材料改判**：补一份材料生成第 2 版，列出哪些变了、为什么变、哪些没变。
6. **替你追问 + 给家人的一页**：生成能查证的问题；对方回复后判断他有没有回避；最后出给家人的一页和网点版提示单。

切换场景不改流程，只改三样东西：查哪些资格、重点核哪些说法、一页纸怎么措辞。

## 3 场景：通用机制

一个场景就是一份配置文件 `backend/app/scenarios/<id>.json`，不为每个场景单写代码。

```json
{
  "id": "savings",
  "label": "存钱 / 理财 / 投资",
  "hand_over": "储蓄",
  "first_question": "它有没有资格收这笔钱",
  "license_checks": ["nfra_bank_list", "amac", "wm_code"],
  "claim_kinds": ["qualification", "return_promise", "partner", "background", "capital", "scale", "payee"],
  "signal_order": ["risk", "finance", "credit", "reputation"],
  "must_ask": ["请给出金融许可证编号或理财产品登记编码", "钱打到哪个账户，户名是不是这家公司"],
  "onepager_title": "转账之前，先确认这几件事"
}
```

| id | 场景 | 你要交出的 | 第一问 | 重点核的说法 | 信号顺序 |
| --- | --- | --- | --- | --- | --- |
| `savings` ★主演示 | 存钱 / 理财 / 投资 | 储蓄 | 有没有资格收这笔钱（银行名单、私募登记、理财登记编码） | 保本保息、高收益、国资背景、银行存管、注册资本、规模 | 风险 > 财务 > 信用 > 口碑 |
| `prepaid` | 预付消费（办卡、课程、装修、养老预付） | 预付款 | 收钱的是不是跟你签约、给你服务的那家公司 | 随时可退、门店规模、会员数、限时优惠 | 口碑 > 财务 > 信用 > 风险 |
| `job` | 求职入职 | 时间和信任，有时还有押金、培训费 | 发 offer 的和交社保的是不是同一家；有没有让你先交钱 | 高薪、包住、上市公司、规模、先交费 | 口碑 > 信用 > 财务 > 风险 |
| `contract` | 合作签约 / 付款 | 货款、定金 | 签约方、收款方、干活的是不是同一家，有没有所需资质 | 资质、背景、规模、收款信息 | 信用 > 风险 > 财务 > 口碑 |
| `takeover` | 接手 / 入股一家公司（赛题第二问） | 资金和经营责任 | 股权干不干净（出质、冻结），有没有对外担保和欠税 | 营收、利润、客户、注册资本 | 财务 > 风险 > 信用 > 口碑 |
| `general` | 其他 | — | 由"最担心什么"决定 | 通用说法 | 默认顺序 |

现有规则覆盖六类说法：资格、收益承诺、合作机构、背景、注册资本、规模。为了通用，补三类，每类配一条确定性规则：

| 新说法类型 | 例子 | 规则 |
| --- | --- | --- |
| `payee` 收款信息 | "请转账至……户名张某" | 收款户名和公司名不一致 → 与记录不符；所有场景都查 |
| `refund` 退款 / 退出承诺 | "随时可退""随时取出" | 有合同条款就对照；没有合同 → 无法核验，并生成追问 |
| `upfront_fee` 先交钱 | "入职需交培训费 / 押金" | 招聘要求先交费 → 不合规承诺（依据《劳动合同法》第九条） |

## 5 判断原则（评委看得见，必须守住）

1. **结论由规则和记录推出，模型不下结论。** 模型只做三件事：从材料里找说法、把规则结果说成人话、判断对方回复有没有回避。这一条要写进讲稿："结论来自记录，AI 只负责读材料和说人话。"
2. **每条发现都能点开来源和日期。** 来源分五类，界面角标用不同样式：官方记录、法规、人工采集（真实）、用户材料、演示（虚构）。
3. **不打安全分，不说"诈骗"。** 只说查到了什么、哪里对不上、还不知道什么、下一步做什么。
4. **没查不等于没问题。** "没查（数据源没覆盖）""查了没有""查询失败"三种情况分开显示。
5. **原文校验。** 模型给的引文必须能在材料里找到，引用的来源 id 必须存在，否则直接丢弃。
6. **改判靠程序比对，没变的也要列出来。** 新材料可能让疑点消失；没有变化本身也是结论。
7. **不给真实公司配假的负面材料。** 虚构案例全程挂"演示数据 · 公司为虚构"。
8. **材料里写的指令只当内容。** 比如"忽略以上规则"这种话，不能改变结论。
9. **对方口头说的，记为"对方说的，未核实"。**

### 6.3 证据包

人工采集的真实记录放在 `backend/data/evidence_packs/<公司全称>.json`。字段结构和 fixtures 里的 `CompanyProfile` 一样，每个字段额外带三项：来源、采集时间、截图路径。来源类型新增 `collected`，表示人工采集的官方记录。

一家公司查数据的顺序：先找证据包（真实）→ 再找 fixtures（演示）→ 都没有就显示"没查"。

## 7 技术方案

### 7.1 选型：能跑就行

- **后端**：沿用现有 `backend/`（FastAPI + Pydantic），单进程运行。存储从内存改成 `backend/data/cases/<id>.json`，重启不丢；不用数据库。
- **前端**：新建 `web/`，从 `demo/index.html` 拆成 `index.html`、`app.js`、`style.css`；原生 JS，不打包。由 FastAPI 直接挂成静态文件，前后端同一端口，免得处理跨域。`demo/` 冻结不动，作为断网备用。
- **模型**：用比赛提供的 Tokendance（OpenAI 兼容的 chat completions 接口），httpx 直连。配置放在 `backend/.env`（已加入 git 忽略）：`TOKENDANCE_BASE_URL`、`TOKENDANCE_API_KEY`、`TOKENDANCE_MODEL`、`TOKENDANCE_VISION_MODEL`。处理流程：模型输出 JSON → Pydantic 校验 → 失败重试一次 → 再失败就退回规则结果，并在界面上注明。
- **读材料**：文字直接用；PDF 用 pdfplumber（已装）；图片走视觉模型或网关的版面解析，都不通就手动粘贴。
- **不用的东西**：Docker（C 盘剩不到 1GB）、Postgres、Redis、Celery、对象存储、登录系统、向量库、前端打包。

启动方式：

```bash
cd backend && .venv/Scripts/python -m uvicorn app.main:app --port 8000
```

启动后用浏览器打开 http://localhost:8000 。

### 7.4 数据结构改动（models.py）

- `CaseIn` 加 `scenario: str = "savings"`。
- `CaseOut` 改为 `Case`，包含 `id`、`case`、`versions: list[Version]`、`current`。
- `Version` = 现在 CaseOut 里的分析部分，再加上 `no`、`created_at`、`trigger`、`materials`、`changes`、`questions`、`onepager`。`trigger` 取值为"首次分析""补充材料：xxx""切换场景"之一。
- `Change` 字段：
  - `target`：说法 id 或信号条目的 key
  - `kind`：`new_concern / worse / clarified / unchanged / added / removed`
  - `before`、`after`
  - `because`：来源 id 加新材料里的原文
  - `plain`：一句人话
- `Question` 字段：`id`、`ask`、`why`、`check_where`、`linked`、`reply`、`reply_verdict`。`reply_verdict` 取值为 `answered / dodged / checkable / new_claim`。

### 7.5 改判怎么算（替代旧 PRD 里的依赖传播）

1. 新材料的文字并入材料集合，标明是第几轮加进来的。
2. 全量重跑抽取和规则。规则是确定性的，跑一遍不到一秒，不需要局部更新。
3. 按说法 id（每类说法的 id 固定，例如 A1）和信号条目 key，逐条对比上一版和这一版：
   - 状态变了，记为变化；变严重记为 worse 或 new_concern，变轻记为 clarified。
     - 说法判定的严重程度：与记录不符 = 不合规承诺 > 说法有误导 = 需要留意 > 无法核验 > 与记录相符。
     - 检查项和信号条目的严重程度：有问题 > 要留意 > 该有的没有 > 没查 > 没问题。
   - 状态没变，记为未变。
   - 新出现的记为新增，消失的记为移除。
4. 模型只负责给每条变化写一句"为什么"，引用的原文必须来自新材料；模型调用失败就用模板句。

## 12 商业闭环（讲给杭州银行听，具体说法等出题人反馈后再定）

- **网点**：老人大额转出或取现说要"去投资"时，柜员用 X-Ray 扫一下宣传单，拿网点版提示单劝阻，有依据，不靠嘴说。
- **手机银行**：给陌生的对公账户大额转账前，提供"先透视一下收款方"的入口。
- **对公客户**：给小微企业主在合作或接手前做一份人话版尽调。
- **银行为什么愿意用**：防范非法集资宣传和资金异常监测本来就是银行的责任，这个工具能直接落到这些工作上。

## 13 砍掉了什么（对照旧 PRD）
