# X-Ray 黑客松版 PRD（48H 施工单）

- 日期：2026-10-02　版本：H2
- 本版根据团队确认的主线改写，流程是：输入企业名称和需求 → 报告和原始数据 → AI 助手问答 → 补充信息后的二次分析；一次只看一家公司。
- 施工以本文为准。[旧版 PRD](2026-10-02-xray-prd.md) 和三份交接文档只作原则参考，冲突时以本文为准。
- 取舍标准只有一条：**评委在 3 分钟演示里看得见的，或者能防止演示翻车的，才做。**

## 0 一句话

把钱或信任交给一家公司之前，输入它的名字，再说一句你要做什么。X-Ray 会把散在各处的真实记录汇到一起，对照这家公司的说法，按你的需求交出一份看得懂的报告，每条结论都能点开原始数据。看完不明白可以问 AI 助手；有了新情况，补充进来，判断会更新，并标出哪里变了、为什么变。

## 1 贴题对照

赛题（杭州银行「X-Ray | 透视·真相」）里的每个关键词，都要对应到一个功能上。

| 赛题原话 | 我们怎么回答 | 对应功能 |
| --- | --- | --- |
| 家人和朋友把储蓄、信任交给一家公司 | 需求里写清替谁看、交出什么；主演示用储蓄理财案例；报告最上面是给家人看的一页 | 输入、一页结论 |
| 你凭什么判断它靠得住 | 不靠感觉，也不靠 AI 打分，而是把它的说法和官方记录逐条对照 | 宣称 vs 记录 |
| 即将接手一家公司，看懂财务、识别风险 | 需求是"接手/入股"时，报告以财务和风险为主，从登记和年报里找财务压力的迹象 | 场景模板、财务信号 |
| 财务、信用、风险、口碑 | 四张信号卡，名字照抄赛题 | 报告第二层 |
| 散在各处的线索 | 监管名单、公示、年报、处罚、投诉、公司自述、用户材料汇进一个案卷，原样保留 | 原始数据 |
| 人人可懂 | 报告分层，先给一页人话结论；不懂的直接问助手 | 一页结论、AI 助手 |
| 从金融视角出发 | 第一问永远是"它有没有资格收这笔钱"，每条规则写明法规出处 | 资格核验、规则库 |

## 2 主线（所有场景共用）

| 步骤 | 用户做什么 | 系统给什么 |
| --- | --- | --- |
| ① 输入 | 填企业名称和一句需求，例如"我妈想在这家公司存 20 万理财，最怕急用时取不出来"。宣传单、合同、聊天截图可以选择性上传，不是必填 | 从需求里识别场景和关注点，用户可以改 |
| ② 汇集数据 | 等待 | 显示正在查哪些来源、哪些查到了、哪些没查到 |
| ③ 报告 | 从上往下看 | 分四层：一页结论 → 四个信号 → 宣称 vs 记录 → 原始数据。每条结论都能点进它依据的原始数据 |
| ④ AI 助手 | 直接提问，或选中报告里的某一条再问 | 只根据本案已收集的数据回答，每句关键事实标出处；不知道就直说，并提议补查或补充材料；也能生成"该问对方的问题" |
| ⑤ 二次分析 | 补充信息：新材料、对方的回复、修改后的需求 | 生成新版报告，并给出变化清单：哪些判断变了、为什么变、哪些没变 |

报告各层的内容：

1. **一页结论**：最多 5 条，分三栏：查到了什么、哪里对不上、还不知道什么；末尾写"在下一步之前先确认这几件事"。这一页可以打印，直接拿给家人看。
2. **四个信号**：财务、信用、风险、口碑，每张卡一句人话，下面列出带来源的明细。
3. **宣称 vs 记录**：对方的每条说法都有一个判定，取值和现有代码一致：与记录不符、不合规承诺、说法有误导、需要留意、无法核验、与记录相符。另外单列一张清单，列出"该有却没写"的内容，例如理财产品的风险提示语。
4. **原始数据**：每个来源一条记录，包括原文或字段、来源链接、采集时间、真实还是演示的标记，以及截图（如有）。

"宣称"有两个来源：一是用户上传的材料；二是公司自己公开的说法，比如官网、招聘页、宣传页（P1，要等网关的搜索能力测通）。两者都没有时，"宣称 vs 记录"这一层显示"还没有这家公司的说法，上传宣传材料或合同就能对照"，报告其余部分照常生成。

## 3 场景：从需求里识别，靠配置实现通用

用户不用手动选场景。系统先从需求里识别场景：模型识别为主，关键词规则兜底；识别结果显示在输入框下方，用户可以改。一个场景就是一份配置文件 `backend/app/scenarios/<id>.json`，不为每个场景单写代码。场景只影响三件事：查哪些资格、重点核哪些说法、报告的排序和措辞。

```json
{
  "id": "savings",
  "label": "存钱 / 理财 / 投资",
  "keywords": ["理财", "存钱", "投资", "收益", "利息", "养老钱"],
  "hand_over": "储蓄",
  "first_question": "它有没有资格收这笔钱",
  "license_checks": ["nfra_bank_list", "amac", "wm_code"],
  "claim_kinds": ["qualification", "return_promise", "partner", "background", "capital", "scale", "payee"],
  "signal_order": ["risk", "finance", "credit", "reputation"],
  "must_ask": ["请给出金融许可证编号或理财产品登记编码", "钱打到哪个账户，户名是不是这家公司"],
  "onepager_title": "转账之前，先确认这几件事"
}
```

| id | 场景 | 你要交出的 | 第一问 | 重点核的说法 | 信号顺序 |
| --- | --- | --- | --- | --- | --- |
| `savings` ★主演示 | 存钱 / 理财 / 投资 | 储蓄 | 有没有资格收这笔钱（银行名单、私募登记、理财登记编码） | 保本保息、高收益、国资背景、银行存管、注册资本、规模 | 风险 > 财务 > 信用 > 口碑 |
| `prepaid` | 预付消费（办卡、课程、装修、养老预付） | 预付款 | 收钱的是不是跟你签约、给你服务的那家公司 | 随时可退、门店规模、会员数、限时优惠 | 口碑 > 财务 > 信用 > 风险 |
| `job` | 求职入职 | 时间和信任，有时还有押金、培训费 | 发 offer 的和交社保的是不是同一家；有没有让你先交钱 | 高薪、包住、上市公司、规模、先交费 | 口碑 > 信用 > 财务 > 风险 |
| `contract` | 合作签约 / 付款 | 货款、定金 | 签约方、收款方、干活的是不是同一家，有没有所需资质 | 资质、背景、规模、收款信息 | 信用 > 风险 > 财务 > 口碑 |
| `takeover` | 接手 / 入股一家公司（赛题第二问） | 资金和经营责任 | 股权干不干净（出质、冻结），有没有对外担保和欠税 | 营收、利润、客户、注册资本 | 财务 > 风险 > 信用 > 口碑 |
| `general` | 其他 | — | 由需求里"最担心什么"决定 | 通用说法 | 默认顺序 |

现有规则覆盖六类说法：资格、收益承诺、合作机构、背景、注册资本、规模。为了通用，再补三类，每类配一条确定性规则：

| 新增说法类型 | 例子 | 规则 |
| --- | --- | --- |
| `payee` 收款信息 | "请转账至……户名张某" | 收款户名和公司名不一致，判"与记录不符"；所有场景都查 |
| `refund` 退款或退出承诺 | "随时可退""随时取出" | 有合同条款就对照条款；没有合同判"无法核验"，并生成要问对方的问题 |
| `upfront_fee` 先交钱 | "入职需交培训费 / 押金" | 招聘时要求先交费，判"不合规承诺"，依据是《劳动合同法》第九条 |

## 5 判断原则（评委看得见，必须守住）

1. **结论由规则和记录推出，模型不下结论。** 模型只做四件事：理解需求、从材料里找出对方的说法、把规则结果说成人话、回答助手里的提问。讲稿里要有这句："结论来自记录，AI 只负责读材料和说人话。"
2. **每条结论都能点进原始数据，并看到日期。** 来源分五类，界面角标要区分开：官方记录、法规、人工采集（真实）、用户材料、演示（虚构）。
3. **不打安全分，不说"诈骗"。** 只说四件事：查到了什么、哪里对不上、还不知道什么、下一步做什么。
4. **没查不等于没问题。** "没查（数据源没覆盖）""查了没有""查询失败"三种情况分开显示。
5. **AI 助手只用本案数据回答。** 关键事实必须附出处；数据里没有的，回答"没查到"，不许凭常识编。
6. **对话不会直接改变结论。** 用户在对话里提到的新情况，要点"加入案卷"才会触发二次分析，报告不会被聊天内容悄悄改掉。
7. **原文要校验。** 模型给出的引文必须能在材料里逐字找到，引用的来源 id 必须存在，否则直接丢弃。
8. **二次分析由程序比对两版得出，没变的也要列出来。** 新信息也可能让疑点消失；"没有变化"本身也是一个结论。
9. **不给真实公司配假的负面材料。** 虚构案例全程挂"演示数据 · 公司为虚构"。
10. **材料里写的指令只当内容。** "忽略以上规则"之类的话不能改变结论。对方口头说的，记为"对方说的，未核实"。

### 6.3 证据包与原始数据

- 人工采集的真实记录放在 `backend/data/evidence_packs/<公司全称>.json`。字段结构和 fixtures 里的 `CompanyProfile` 相同，每个字段额外带来源、采集时间和截图路径。来源类型新增一个 `collected`，表示人工采集的官方记录。
- 查一家公司时按顺序找：先找证据包（真实），再找 fixtures（演示），都没有就显示"没查"。
- 每次取数据都在案卷里写一条原始记录（RawRecord），报告第四层就是展示这些记录。

### 6.4 演示案例（最重要的一件事，由产品负责人亲自盯）

| 案例 | 作用 | 要求 |
| --- | --- | --- |
| A 主线（真实） | 讲储蓄托付 | 选一家已被法院判决或监管通报认定的非法集资相关公司。输入：公司名 + "我妈想存 20 万理财"；材料用公开报道或判决书里引用的宣传话术。界面写清资料截止日期和话术出处。只讲当时就查得到的项（经营范围、实缴资本、持牌名单、私募登记）；事后才出现的记录（如吊销）要单独标出 |

| C 备用（虚构） | 演示二次分析、断网兜底 | 就是满盈禾。如果真实案例凑不出能"补充"的材料，就用它演示二次分析，并全程挂虚构标记 |

## 7 技术方案

### 7.1 选型：能跑就行

- **后端**：沿用现有 `backend/`（FastAPI + Pydantic），单进程运行。存储从内存改成 `backend/data/cases/<id>.json`，重启不丢数据，不用数据库。
- **前端**：新建 `web/`，从 `demo/index.html` 拆成 `index.html`、`app.js`、`style.css`；原生 JS，不打包。由 FastAPI 直接挂成静态文件，和后端同一个端口，不用处理跨域。`demo/` 冻结不动，作为断网时的备用演示。
- **模型**：比赛提供的 Tokendance（OpenAI 兼容的 chat completions 接口），用 httpx 直接调用。配置放在 `backend/.env`（已加入 git 忽略）：`TOKENDANCE_BASE_URL`、`TOKENDANCE_API_KEY`、`TOKENDANCE_MODEL`、`TOKENDANCE_VISION_MODEL`。模型输出 JSON 后用 Pydantic 校验；校验失败重试一次，还失败就退回规则结果或模板，并在界面上注明。
- **AI 助手的上下文**：一个案卷的数据量很小，直接把整份报告和原始数据放进上下文，不用向量库。
- **读材料**：文字直接用；PDF 用 pdfplumber（已装）；图片走视觉模型或网关的版面解析，都不通就让用户手动粘贴。
- **不用**：Docker（C 盘只剩不到 1GB）、Postgres、Redis、Celery、对象存储、登录系统、向量库、前端打包工具。

启动：

```bash
cd backend && .venv/Scripts/python -m uvicorn app.main:app --port 8000
```

然后用浏览器打开 http://localhost:8000 。

### 7.4 数据结构改动（models.py）

- **CaseIn**：新增 `need`（一句需求）和可选的 `scenario`；原有的 `concern` 并入 `need`；`flyer_text` 改名为 `material_text`。
- **Case**：取代现在的 CaseOut，字段为 `id`、`case`、`scenario`、`focus`、`versions: list[Version]`、`current`、`raw: list[RawRecord]`、`chat: list[ChatMessage]`。
- **Version**：现有 CaseOut 的分析部分，再加 `no`、`created_at`、`trigger`、`changes`、`questions`、`onepager`。`trigger` 取值为：首次分析、补充材料、对方回复、修改需求。
- **RawRecord**：`id`、`source_id`、`title`、`kind`（official / collected / user_material / web / demo）、`retrieved_at`、`url`、`content`（原文或字段）、`screenshot`。
- **ChatMessage**：`role`、`text`、`refs`（用户选中的条目）、`citations`（回答引用的 RawRecord 或报告条目 id）、`created_at`。
- **Change**：
  - `target`：说法 id 或信号条目的 key
  - `kind`：`new_concern / worse / clarified / unchanged / added / removed`
  - `before`、`after`
  - `because`：RawRecord id，加上新信息里的原文
  - `plain`：一句人话说明
- **Question**：`id`、`ask`、`why`、`check_where`、`linked`。

### 7.5 二次分析怎么算（替代旧 PRD 的依赖传播）

1. 把补充信息写进案卷：新材料和对方回复都记为一条 RawRecord，对方回复标注"对方说的，未核实"；修改需求则重新识别场景和关注点。
2. 全量重跑抽取和规则。规则是确定性的，跑一遍不到一秒，不需要局部更新。
3. 按说法 id（每类说法的 id 固定，例如 A1）和信号条目 key，逐条比对上一版和这一版：
   - 状态变了，记为变化：变严重记为 worse 或 new_concern，变轻记为 clarified。
     - 说法判定的严重程度：与记录不符 = 不合规承诺 > 说法有误导 = 需要留意 > 无法核验 > 与记录相符。
     - 检查项和信号条目的严重程度：有问题 > 要留意 > 该有的没有 > 没查 > 没问题。
   - 状态没变，记为 unchanged。新出现的记为 added，消失的记为 removed。
   - 只改了需求时，事实层面没有变化，变的是报告的排序和措辞。变化清单要明确写出"事实没变，看的重点变了"。
4. 模型只负责给每条变化写一句"为什么"，引用的原文必须来自新信息；模型调用失败就用模板句。

## 12 商业闭环（讲给杭州银行听，等出题人反馈后再定稿）
