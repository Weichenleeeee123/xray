## 1 产品目标和价值

### 1.1 产品定义

X-Ray 围绕一次具体决定，搜集并解释企业与交易信息，持续维护有证据、有适用范围、可修订的判断，帮助用户明确下一步需要核实什么。

产品主对象是“决策任务”，英文和代码统一使用 `case`。一个 case 可以包含多个公司、多个方案、多份材料、多个分析版本和一段连续对话。不得在接口中混用 project、task、case 表示同一业务对象；后台执行使用 `run`，核验待办使用 `action_item`。

### 1.2 必须达成的结果

1. 用户能用自然语言开始调查指定公司，或发现符合条件的候选公司。
2. 相同公司在不同目标下呈现不同的检查重点和解释，但不改变原始事实。
3. 用户能从每条重要判断进入对应证据，而不是只拿到一份不可追溯的报告。
4. 用户能引用页面中的判断、数据或条款向 AI 提问。
5. Agent 能补充调查，并把表格、图表、比较和清单保存到工作台。
6. 新材料进入后，系统说明哪些判断改变、为什么改变、什么没有改变、还缺什么。
7. 比较表、趋势和待办能跟随判断版本更新，不留下无提示的旧结果。
8. 注册用户能保存和恢复任务；公开部署不导致私人材料公开。

### 1.3 核心创新

创新集中在“有依据的判断持续更新”，而非宣称首次实现企业查询、RAG 或合同摘要。公司公开资料正常，不代表本次签约、付款或履约关系已经确认。新材料既可能增加疑点，也可能澄清疑点；没有变化也是有效分析结果。

产品展示的是事实依据、适用条件、具体影响和核实行动，不提供无校准依据的企业安全总分、诈骗概率或兜底保证。

## 2 用户和关键旅程

### 2.1 用户角色

| 角色 | 可用能力 | 权限 |
| --- | --- | --- |
| 未登录访客 | 阅读介绍与已审查的公开案例，输入尚未提交的需求 | 不读取私人 case；输入草稿登录后可带回，不在浏览器长期保存敏感附件 |
| 注册用户 | 创建与管理自己的 case、上传、分析、问答、比较、导出、删除 | 仅访问自己的私有资料及合法公开资料 |
| 运维管理员 | 查看服务状态、脱敏错误、配额和任务运行情况 | 默认不开放用户原文浏览；排障访问必须有授权与审计记录 |

本版不引入团队协作权限或社会化公司评分。一个用户可分析家人的材料，但应有材料使用许可，且不得假装完成材料涉及人员的身份认证。

### 2.2 旅程 A 指定公司

输入“我准备向 A 公司支付一笔服务费，最在意能否退款” → 生成可编辑任务摘要 → 确认法定主体 → 保存任务并研究 → 阅读当前判断 → 查看原文 → 追问 → 生成付款前核验清单。

### 2.3 旅程 B 寻找和比较候选

输入“找杭州可以实习的智能硬件公司” → 提取地区、行业、目的和偏好 → 有阻断歧义才追问 → 检索有来源的候选 → 加入或移出比较 → 对齐比较维度 → 查看每个单元格依据 → 调整优先事项并保存选择理由。

### 2.4 旅程 C 新材料改变判断

进入已有 case → 上传新合同、聊天或付款截图 → 检查关键字段识别结果 → 系统关联当前主体与交易 → 展示复核进度 → 发布新版本 → 对照新增、改变、撤回、未变和未知项 → Agent 补查并更新相关成果。

### 2.5 旅程 D 恢复和持续关注

重新登录 → 打开历史 case → 恢复最后已发布版本 → 看到资料时间和待办 → 手动刷新或开启关注 → 新公开资料通过同一个更新流程进入 → 有实质变化才产生提醒。

### 3.1 分析边界作为行为规则

- 输出具体问题、可能影响、信息缺口和核实办法，不以“安全”“诈骗”“必然违约”代替证据分析。
- 用户要求比较时提供条件化建议，例如“更符合你已确认的退出灵活性偏好”；不把个人适合度等同于公司信用。
- 不自动付款、签约、申请职位或向第三方发送用户材料；可以生成询问话术。
- 截图能支持“图中显示什么”，不自动完成户主认证、文件鉴真或交易结算确认。
- 资料不足、未接入、访问失败、尚未提供分别记录；都不等于“未发现风险”。

## 4 统一术语和状态

### 4.1 核心术语

| 术语 | 定义 |
| --- | --- |
| case | 用户的一次决策任务，可以跨公司、跨方案，默认私有 |
| entity | 公司、品牌或自然人等主体；自然人仅在当前授权任务材料范围内处理 |
| role | 主体在本次交易中的身份，如签约方、收款方、雇佣方、履约方 |
| document / document_version | document 是材料身份；每个 document_version 是不可静默覆盖的来源版本，记录原文、文件及时间 |
| evidence | 文档中的可定位原文片段或图片区域 |
| observation | 材料中提取的原子陈述，不因名称为事实字段就视为已证实 |
| claim | 面向当前目标的判断，包含依据、前提、限制和状态 |
| assessment | 同一输入快照下发布的一组判断与派生成果引用 |
| artifact | 可独立打开、保存、导出的表格、图表、比较或清单 |
| run | 一次可追踪的后台操作，不等于 case |
| action_item | 用户需要进一步核实、补充或完成的事项 |

### 4.2 枚举和状态机

统一使用以下机器值，前端维护中文显示映射，不发送翻译后的文字作为枚举。

| 对象／字段 | 允许值 | 规则 |
| --- | --- | --- |
| scenario | `employment / rental / partnership / investment / consumption / contracting` | 主场景一个，可记录附加关注点；切换生成 context 新版本 |
| case.lifecycle | `draft / active / archived / deleting` | 归档可恢复；彻底删除不可作为恢复功能 |
| case.decision_stage | `exploring / comparing / preparing_contract / preparing_payment / following / completed` | 业务阶段由用户或确认后的建议改变，不与运行状态混用 |
| run.status | `queued / running / awaiting_user / succeeded / partial / failed / cancelling / cancelled / superseded` | 终态不可被晚到事件回写为 running |
| run.stage | `planning / discovering / fetching / parsing / extracting / comparing / checking / synthesizing / validating / publishing` | 可并行分支；进度为阶段和计数，不伪造精确百分比 |
| document.processing_status | `awaiting_upload / uploaded / validating / queued / parsing / indexing / ready / partial / needs_review / failed` | 处理状态与可访问性分开；部分页失败为 partial |
| document.availability | `active / withdrawn / deleting / deleted` | 撤回表示不再用于当前判断，删除表示清理内容 |
| observation.verification | `source_reported / independently_supported / computed / user_confirmed_transcription / disputed / unresolved` | 用户确认识别正确不升级为现实真实性认证 |
| claim.status | `supported / conditional / needs_verification / conflicting / withdrawn / source_removed` | supported 仅表示在当前证据和范围内得到支持 |
| claim.attention | `informational / review_before_decision / review_before_payment` | 表示核实优先级，不表示诈骗概率 |
| change.kind | `added / strengthened / weakened / contradicted / superseded / clarified / scope_changed / unchanged / withdrawn` | 一次变化可有一个主类型及附加标签 |
| artifact.status | `current / updating / stale / failed / withdrawn` | 始终带 based_on_version；旧成果不会无提示冒充最新 |
| action_item.status | `open / in_progress / user_marked_done / resolved / dismissed / reopened` | 用户勾选完成不等于证据已核实；resolved 需要依据或明确的范围说明 |
| source.fetch_status | `available / not_disclosed / not_covered / fetch_failed / user_pending` | 缺失原因必须保留 |
| ingestion_batch.status | `open / sealed / awaiting_review / committed / cancelled` | 封批固定成员；确认纳入后才形成一次输入修订 |
| operation.status | `proposed / awaiting_confirmation / approved / executing / succeeded / rejected / expired / failed` | 用户确认不是执行成功；过期后重新提议 |

`draft → active → archived → active` 是正常生命周期；任一非 deleting 状态可进入 deleting。run 被取消不删除已发布 assessment，失败保留最后一版完整结果。用户补充确认后可以恢复 awaiting_user 的操作，但恢复时必须再次校验输入版本。

### 5.2 FR-01 账户

输入：用户名、密码；邮箱可在注册时提供，也可后续绑定。用户名去首尾空格后按不区分大小写唯一，3—32 字符。密码 12—128 字符，不在日志中记录。昵称与登录用户名分开。

行为：

1. 用户名密码注册可以独立完成，不依赖邮箱即时送达。
2. 填写邮箱不等于已验证；只有点击一次性验证链接或提交有效验证码后标记 verified。
3. 邮箱验证令牌有效期 30 分钟，重置令牌 15 分钟，数据库只保存令牌哈希；重复使用失败。
4. 只有已验证邮箱可以用于找回密码；没有绑定时界面明确说明当前无法通过邮箱恢复，不假装发送邮件。
5. 登录成功进入 `/app`，会话由后端 Cookie 维持；退出和改密撤销对应会话，改密默认撤销其他会话。
6. 密码重置请求对不存在的邮箱也返回相同说明，避免暴露账号是否存在。

验收：注册后能登录并创建任务；注销后受保护 API 返回 401；第二账户无法读取第一账户的 case；邮箱未验证不能用于接管账号。

### 5.3 FR-02 任务首页

每条任务显示标题、场景、阶段、候选摘要、最后更新时间、最后已发布版本、运行状态和未处理提醒数。支持按关键词、场景、生命周期筛选；默认最近更新排序，游标分页。

空状态提供自然语言入口和六种场景示例，不显示虚构任务。卡片打开最后已发布版本；任务正在运行时同时恢复进度。归档只是隐藏出默认列表，不删除对话和证据。复制任务默认复制目标和模板，是否携带原有材料由用户明确选择；新任务没有原任务的运行历史。

### 5.4 FR-03 创建任务

自然语言解析输出 `title / scenario / decision_stage / target_names / constraints / priorities / questions / entry_mode`。entry_mode 为 `specified / discovery / mixed`。

前端展示可编辑摘要。用户可以修改公司、场景、关注点、期限和金额；非必要字段允许未知。系统只在以下情形要求先确认：多个高度相似主体无法消歧、用户要求的地区或对象范围完全不明确且影响查询、识别结果与用户输入明显冲突。

指定公司流程：主体候选展示全名、地区、官网或可靠来源、可获取的统一信用代码等；用户确认后建立 entity 和 case 角色。发现候选流程：按可用来源返回默认 5 个候选，每个有匹配理由、至少一条可打开来源、已满足和待确认条件；支持继续寻找，不声称覆盖全市场。混合流程保留已有候选并发现新候选。

不确定的画像或条件只能作为“建议”显示。用户点击“开始分析”后保存 context 快照并创建 initial_research run；列表中立即能看到任务。

### 5.5 FR-04 主体和候选管理

区分品牌、法定公司、分支机构、自然人和未知主体。关系带来源及有效期间，不因为名字相似就认定关联。展示“我调查的公司”“材料中的签约方”“材料中的收款方”“履约方”等角色。

允许添加、移出和恢复候选；移出只影响当前比较，不删除材料。材料提取出新主体时先匹配已有实体，再产生待确认候选。自然人材料只在当前授权任务内使用，不建立面向全站的私人信用档案。

### 5.6 FR-05 研究总览

固定信息层次：当前任务与数据范围 → 关键判断 → 支持与不利线索 → 未知和未覆盖项 → 下一步核实。每条重要判断带原文引用、资料时间、适用主体和限制。

字段包括可获取的登记信息、经营与公开财务线索、公开争议、交易角色、付款与退出条件。无数据的字段显示具体原因，不填 0。公司自述、监管记录、企业自行披露、媒体报道和用户材料用不同来源类型标记。

查询失败只影响对应来源；其他已完成结果可发布 partial，并注明未完成范围。默认不生成“公司安全分”。适配性比较以已确认偏好和可核对维度表达，未知不按低风险计分。

### 5.7 FR-07 画像

画像分 `case_context` 与 `global_profile`。本次明确输入可直接用于本次任务；对话或材料推断出的长期偏好先生成 memory suggestion，用户接受后才写入 global_profile。

每条偏好含 value、来源、explicit/inferred、scope、created_at、updated_at、有效性。用户可停用、修改和删除；每次任务展示使用了哪些长期偏好。允许选择自己的某个历史 case 作为上下文，默认不跨任务读取合同全文或敏感字段。

修改偏好只改变排序、适用性和解释，不改写原始材料。context 版本改变后，相关判断和比较进入复核；与该偏好无关的资料不重抓。

### 5.8 FR-08 解释层

指标、术语和判断支持“含义”“与你有关的原因”“来源与限制”三部分。基础定义优先来自维护好的术语库；个性化解释使用当前 case 证据。鼠标悬停可预览，点击和键盘聚焦可打开完整解释，移动端不依赖 hover。

解释通常为 1—3 句，完整深挖进入任务助手。解释失败时保留基础定义和原始来源，不阻塞页面。术语缓存按术语版本和语言管理，个性化解释必须额外绑定 context/assessment 版本。

### 5.9 FR-09 任务内助手

输入允许普通文字及所选内容引用；最多同时引用 10 个页面对象。引用对象可以是 claim、observation、evidence、artifact cell，携带 ID 与版本，不传整个 DOM。

助手分 explain、research、compare、trend、checklist、reassess 等意图。解释已有内容不必新建 assessment；补搜和复核进入 run；生成成果保存 artifact。执行进度显示工具名称、目的和结果摘要，不把模型内部推理文本当作可审计证据。

回答引用失效、被删除或版本较旧时先说明并提供当前版本入口。写回完成提供明确回执和跳转。模型文字本身不成为已证实事实；用户口述记录 source_type=user_text、verification=source_reported，界面注明“用户提供，未独立核实”。

### 5.10 FR-10 材料中心

支持 PDF、DOCX、JPG、PNG、HTTPS 网页 URL 和粘贴文本。单文件默认上限 25 MiB、单批 10 个文件、PDF 100 页、粘贴文本 50,000 字符，均为可配置运行值，不作为产品永久上限。超出时显示拆分或调整配置的办法，不静默截断。

每份材料显示文件名、类型、所属主体、交易角色、材料日期、上传时间、处理进度、缺页或低置信提取提示。解析完毕展示关键主体、金额、期限、收款名称和主要条款；用户可以修正识别结果，修正保存为事件，保留原识别并触发复核。

每批先建立 ingestion_batch；客户端完成添加后封批，明确所有成员与放弃的上传。成员均达到 ready/partial/needs_review/failed 或已取消后进入 awaiting_review。partial 可使用已成功页，但必须列明失败范围；needs_review 的关键字段须确认或明确保持未知。用户选择纳入的成员/成功页并确认继续后，整批只形成一次输入修订和一次判断更新；全 ready 可按用户创建批次时确认的 auto_commit 策略自动继续。未封批不自动判断“文件已齐”。

重复上传返回复用提示，不算独立证据；全部为已纳入重复材料时不增加 revision。确认继续后批次不可再添加成员，之后重试成功的页面形成后续批次。不同用户的哈希命中不暴露另一用户是否上传过该文件。

链接抓取结果保存来源与时间；未能取得正文时只保留摘要级证据并明确标记。聊天保留可见说话方、消息时间及上下文，截屏缺页或截断不得推定被省略部分。

### 5.11 FR-11 判断变化

变化页支持版本选择、变化类型筛选、按主体或分析维度筛选。每项变化展示旧表述、新表述、证据变化、适用条件变化和下一步行动。默认突出改变与撤回，未改变的关键判断可展开。

更新中保留旧结果，并标记具体内容正在复核；发布时统一切换 assessment 指针。用户能回看旧版本当时的证据范围，但已彻底删除的内容不得通过历史版本恢复。

### 5.12 FR-12 分析成果

支持 `fact_table / comparison / trend / event_timeline / clause_diff / checklist` 六种 artifact。所有单元格、数据点或条目支持引用。

- 事实表：字段、值、单位、期间、来源和缺失原因。
- 比较：不同公司或同一公司的不同方案；统一维度，显示已满足、未满足、待确认和不适用。
- 趋势：程序计算，列明期间、币种、单位和统计口径；缺失期留空，默认不连线；缺少足够可比点时给数据表和补搜入口。
- 时间线：区分事件发生、文件发布和本次获取时间。
- 条款对照：保留两侧原文与条件差异，不把“日期不同”直接当矛盾。
- 清单：问题、为什么要问、建议材料、状态和依据。

偏好调整可改变比较顺序，但不能把未核实候选排成确定最优。成果以结构化 JSON 交给固定组件渲染，不执行模型生成的 JavaScript、HTML 或 Python。

### 5.13 FR-13 行动清单

行动项包含问题、影响、建议索取材料、优先级、负责人默认为当前用户、可选截止时间、来源引用。用户可复制询问话术、勾选已问、上传回复、标记暂不处理。

“已问过”只进入 user_marked_done；只有新证据覆盖了问题或用户明确接受未知状态后，才形成相应 resolved/dismissed 状态及原因。新材料重新引入冲突时可自动 reopened，并给出依据。

### 5.14 FR-14 历史与导出

任务历史可按标题、公司、场景查询。材料库复用需选目标 case，且生成独立关联，不共享其他 case 的私人分析结论。

导出包括：当前或指定历史版本的 HTML/打印 PDF 报告、UTF-8 CSV 数据表、JSON 结构化数据。报告包含版本、资料范围、来源、未知项及生成时间；不默认附带原始合同。CSV 对可能被表格软件当作公式的单元格进行安全转义。

公开分享不属于当前确认的必要需求；本版导出由用户自行保存，不自动生成可公开访问原文件的链接。

### 5.15 FR-15 更新与提醒

支持用户点击刷新和主动开启 case 关注。关注默认每 6 小时检查已配置来源；间隔可由运维调整，用户可关闭。没有内容变化不重跑完整模型，不通知；获取失败单独显示来源状态，不当作公司风险变化。

提醒包含 analysis_ready、material_needs_review、judgment_changed、action_due、source_unavailable，默认在应用内展示；邮件提醒仅发送给已验证邮箱且经用户启用。提醒不包含完整账号、聊天或合同原文。

### 5.16 所有页面共用状态

loading 显示正在获取的范围；empty 给出下一步；partial 保留已完成内容并显示缺口；error 给重试和错误编号；permission_denied 不泄露对象是否存在；stale 显示基于旧版本；deleting 停止继续分析与导出。键盘操作、上传进度、长表格分页和移动端基本可用均纳入验收，但本 PRD 不指定视觉风格。

## 7 证据与判断规则

### 7.1 来源分层

source_type 固定为 `official_record / company_disclosure / company_website / licensed_api / public_media / user_document / user_image / user_text`。同时保存实际陈述者 publisher/asserter；官方网站载体上的企业自报信息仍标为企业披露。

来源记录区分发布时间、事件时间和获取时间。重复转载关联 canonical_source_id，不按网页数量重复计算独立支持。搜索摘要与已取得正文分别保存；正文缺失时不能伪造页码或引用。

来源被认为权威不意味着自动支持所有推断。例如登记记录可以证明某项公示状态，不能单独证明当前现金余额或本次付款获得授权。

### 7.2 原子信息规范化

Observation 至少包含主体、predicate/metric_key、值、期间、币种与单位、交易角色、适用条件、原文证据和验证状态。主体、数值、条件三者不能只存在于一段摘要里。

数字按 Decimal 处理，API 使用十进制字符串。百分数以 ratio 保存并带显示单位，例如 12% 存值 `0.12`、unit=`ratio`。原文单位和换算公式同时保存。空值必须携带原因；不适用与未知分开。

不同年度、集团与子公司、合并与单体、不同货币、不同购买渠道、草案与已明确替代的新版本，先对齐口径再判断变化。相似名称仅形成实体匹配候选。

### 7.3 引用格式

引用绑定不可静默改变的 evidence_id 与 document_version_id，不保存长期公开下载地址。页码从 1 开始；图片区域使用 0—1 归一化坐标，取左上角和右下角。

```json
{
  "evidence_id": "ev_001",
  "document_version_id": "dv_001",
  "relation": "supports",
  "locator": {
    "kind": "pdf",
    "page_number": 3,
    "bbox": [0.10, 0.20, 0.90, 0.35],
    "paragraph_id": null,
    "message_id": null,
    "quote": "与当前判断直接相关的短原文",
    "prefix": null,
    "suffix": null
  }
}
```

以上短 ID 仅为说明字段关系的示例，线上资源 ID 为 UUID。网页用快照中的 quote＋前后文和段落位置，DOCX 用段落／表格单元格，聊天用消息序号。没有精确坐标时 bbox 为 null，至少能打开真实对应页或原文片段；禁止编造精确定位。

### 7.4 判断发布前的最低检查

1. 所有引用 ID 存在，属于本次允许证据范围，并且未撤回或删除。
2. 原文和定位对应；模型凭空添加的引用不得发布。
3. 结论涉及的主体、时期、渠道和条件与引用相符。
4. 有数据计算的判断能回溯到输入 observation 和确定性计算记录。
5. 有相反证据时保留反方和条件，不仅选择支持预设结论的材料。
6. 无证据内容只能保存为明确的待验证假设或问题。
7. 对新材料的差异描述不得从“名称不同”直接跳为“诈骗”。

程序校验负责结构、权限、存在性、数值和版本。语义支持关系由分析与复核节点处理，并通过人工标注样例评估；不宣称加一个审核模型就能消除幻觉。

## 8 新材料更新引擎

### 8.1 输入快照

每个分析 run 固定外部基准 `case_id / base_input_revision / context_version_id / base_assessment_id / scenario_template_version`，并保存 `active_attempt / run_snapshot_id`。case.input_revision 是已纳入 case 的输入修订号；外部上传批次确认纳入、撤回、关键纠错、场景或任务条件改变时增加。接口 run.input_revision 是 base_input_revision 的兼容展示值，不代表未来发布版必然使用同一 revision。

同批解析未结束的文件暂不混入已冻结快照。用户选择按成功文件继续后，失败项不在本轮快照中；后来重试成功形成下一轮。

run 自己搜索取得的来源先通过 A 登记到 `(run_id, active_attempt)` 的 staging，不立即修改 case.input_revision，也不进入其他 run 的可用材料集合。进入比较/判断前建立不可变 run_snapshot，记录当时已授权基础证据和 staging 证据的精确版本集合。初始研究、刷新和增量复核采用同一规则。

冻结后发现需要补搜时可以创建同一 run 的下一个 snapshot_no：完成补搜→生成新快照→使旧候选失效→重新检查所有受新来源影响的判断与引用。不得向旧快照偷偷追加成员。受工具/轮数预算限制，不无限补搜。CandidateAnalysis 必须绑定最新 run_snapshot_id 和 active_attempt。

发布事务先比较外部基准是否仍匹配；若匹配，原子激活本轮有效 staging 来源。存在新的有效来源时将 case.input_revision 增加一次，并将增加后的值写入 assessment；没有新来源则沿用原值。随后写入判断和成果状态并更新 head。若外部输入或 head 已变化，整个事务不激活 staging、不发布旧候选，进入 superseded 后基于最新输入再运行。

### 8.2 处理步骤和模块归属

| 步骤 | 处理 | 负责方 | 输出 |
| --- | --- | --- | --- |
| 1 | 核验文件、权限、重复哈希、批次 | A | 已授权的材料版本和 ingestion run |
| 2 | 提取文字、结构、主体、金额、时间、条款 | B | 带位置的 evidence 和 observation 候选 |
| 3 | 规范化主体与口径；不明确项请求确认 | B，A 保存 | 匹配结果与 needs_review 项 |
| 4 | 与已有命题比较新增、补强、冲突、替代和适用性 | B | proposed change 集合 |
| 5 | 沿依赖边找到受影响范围，并重新检查场景关键项 | A 依赖查询＋B 判断 | affected claim/artifact/action 集合 |
| 6 | 复核相关判断，必要时定向补搜 | B | CandidateAnalysis |
| 7 | 格式、引用、权限、数值、输入快照校验 | A＋B 校验器 | 校验结果 |
| 8 | 原子发布 assessment，更新当前指针和派生状态 | A | 新版本、变化事件和用户提醒 |

### 8.3 影响传播

依赖边支持 `supports / contradicts / qualifies / derived_from / supersedes`。源节点可以是 observation、claim version 或已确认的 context 条件；下游可以是 claim、artifact cell 或 action_item。

程序沿已知依赖找候选影响范围；模型决定语义上应如何修订。对从未出现过的新条款、收款主体、费用或资质问题，还要扫描当前场景检查项，不能因为没有旧边就忽略。无法确认范围时扩大复核并注明，不声称百分之百局部命中。

### 8.4 发布和成果一致性

在数据库事务中锁定 case，确认用户有效、run 未取消、提交 attempt 等于 active_attempt、提交快照等于 run 最新冻结快照、case.input_revision 等于 base_input_revision、context 与外部基准一致、head_assessment 未被其他 run 改变、引用仍可访问。全部满足才按第 8.1 节激活本轮来源、提交新版本并更新指针。

新 assessment 保存完整的 claim version 引用集合；未改变的 claim version 可以复用，不必改写内容。每个新 artifact version 绑定新 assessment 或明确的旧版本。暂时无法重算的旧成果在同一发布事务中标 stale/updating，并禁止作为最新依据导出；不能出现新判断配无标识旧图表。

若运行依据过期，run 标为 superseded，不覆盖新结果；按最新 input_revision 去重安排一次合并复核。若反复有新输入，等待本批材料稳定后再发布，不无限自动循环。

### 8.5 幂等和并发

创建 case、确认上传、创建 run、发送执行型助手消息均接受 Idempotency-Key。相同用户、路由、key 和请求体返回原结果；同 key 不同请求返回 409。worker 重投递允许，但发布具有唯一约束，每次 run 最多发布一个 assessment。

两批材料基于同一旧版本时，先完成的可发布；后完成的进入 superseded 后基于包含两批材料的新快照复核，不能丢掉任一有效输入。自动复核按 case＋revision＋run kind 去重。

承接旧 staging 必须由 A 的 `adopt_staging` 服务执行：创建合并复核 run 时重新检查旧来源的 owner、case、可用性、使用许可和当前目标适用范围，将有效来源登记到新 run/attempt 的 staging，记录 origin_run_id 和 origin_snapshot_id；不修改旧快照，不复用旧候选判断。已激活或内容相同的来源去重。若去重后的合并 run 已存在，将待承接来源加入其受控收集集合，下一次冻结生成新 snapshot 并使旧候选失效；正在发布时以 case 事务锁串行决定纳入本轮还是下一轮。取消/删除明确禁止继续使用的资料不能借承接重新激活。AC-58 必须验证最终快照含两边有效来源，不依赖重新搜索碰巧命中。

用户手动重试 failed/partial/cancelled/superseded 的 run 时总是创建新 run，记录 retry_of_run_id，并基于最新已授权输入建立基准；已成功 run 需要新研究时使用 refresh/followup。未发布运行的自动故障恢复可以增加 active_attempt。所有阶段写入、事件、暂存证据和候选提交携带 attempt；旧 worker 的写入在服务端拒绝，不能抢先发布。一个已发布 partial 的 run 不再追加第二个 assessment，补全通过新 run 发布下一版。

### 8.6 撤回、纠错与彻底删除

- 纠错：追加 correction event，保留原始材料，改变结构化提取版本；用户纠正不是独立外部证明。
- 撤回：用户选择“本任务不再使用”，立即从当前分析范围排除，材料仍可在本人库中管理；新判断复核受影响部分。
- 彻底删除：立即撤销本系统后续读取和新分析权限，停止相关在途结果发布；清理原文件、缩略图、提取文本、切片、向量、缓存摘录、引用摘录及含该私人内容的派生成果。清理范围包含 messages、对话摘要、解释缓存、记忆建议和持久化 SSE payload；按来源依赖定位，依赖不明时清空受影响回答正文。历史只保留不含私人原文的最小删除标记。

私人原文与导出使用鉴权 API 代理读取，每次请求及 Range 请求检查 availability，不发可绕过撤权的对象存储 GET 签名 URL。删除时使代理读取和事件重放立即过滤被删除内容，并通知在线客户端清理相关预览/缓存；已传到用户设备或被用户自行下载的副本无法追回，不能承诺远程删除这些副本。

不可变版本指常规编辑不覆盖正文，不代表保留用户要求删除的敏感内容。备份默认最长 7 天滚动保留，恢复时先执行删除记录再开放读取；界面显示当前存储与备份过期状态，不声称上游模型服务也已立即删除全部日志。

## 9 Agent 工具与行为协议

### 9.1 主 Agent 和分析节点

一个主 Agent 管理对话与研究计划；以下节点可按流程组合或并行：需求理解、主体匹配、资料采集、文档提取、规则检查、语义比较、判断复核、成果生成。各节点不维护独立真相库，共用授权的证据服务。

LLM 负责语言理解、条款语义、调查计划和解释；程序负责权限、实体精确标识校验、金额计算、状态机、幂等、版本发布和导出。工具能力是否使用原生 function calling，由 Tokendance 能力探针决定。

### 9.2 工具清单

| 工具名 | 输入 | 输出 | 权限与副作用 |
| --- | --- | --- | --- |
| resolve_entity | 名称、地区、可用标识 | 主体候选和来源 | 只查授权数据，不能改 owner |
| discover_candidates | 场景、硬条件、偏好、数量 | 有来源的候选 | 创建候选建议，不伪造匹配项 |
| search_sources | 脱敏关键词、域名和时间条件 | URL、标题、摘要与获取状态 | 不向搜索发送账号或私有合同全文 |
| fetch_source | 允许访问的 URL | 原文、发布时间、抓取时间 | SSRF 校验、大小限制、无登录绕过 |
| parse_document | 授权 document version ID | 页级文字、表格、位置和质量 | 不执行文件中的宏或指令 |
| retrieve_evidence | 问题、主体、期间、case 范围 | 可用片段与 evidence ID | 先鉴权过滤再检索 |
| run_scenario_checks | 模板版本、上下文和观察集合 | 检查状态与缺口 | 固定规则和语义分析结合 |
| compute_metrics | 已有 observation ID 与允许算子 | 数值、公式和输入 lineage | 只执行白名单算子，不接受任意代码 |

| propose_claim_updates | 受影响范围与证据 | 候选判断与变化 | 不能直接提交当前版本 |
| build_artifact | 类型、结构化数据与引用 | 待提交 artifact | 仅允许预定义展示结构 |
| propose_actions | 当前未知项和目标阶段 | 核验清单 | 不自动发送给公司 |

### 9.3 自动操作和确认操作

用户当前要求范围内的补搜、生成表格、添加证据和核验清单可自动执行。改变长期画像、切换主要目标、移除重要用户材料、彻底删除和对外披露必须有具体确认。用户明确要求“修改本次优先级为退款”可直接产生 context 新版本，并返回变更回执。

所有工具使用由后端注入的固定授权上下文；模型传入的 owner_id、任意文件路径、SQL 或外部指令无效。网页、PDF 和图片中的命令性文字仅是材料内容。

### 9.4 初始研究流程

确认需求与主体 → 按场景创建调查计划 → 并行查询已授权来源 → 保存来源与片段 → 规范化观察 → 执行场景检查与数字工具 → 生成有引用判断 → 复核 → 发布 → 生成下一步核验事项。

### 9.5 连续问答与记忆

上下文优先顺序为：当前用户明确要求、当前 case 确认条件、当前可用证据、用户选择的长期偏好、相关历史摘要。长对话总结用于导航，不替代原始事实；重要内容必须指回原消息或 evidence。

解释旧版本时明确标识“针对 vN”；涉及当前行动时同时提示有无新版本。没有证据就返回未知或安排补查，不把上一轮模型自己的输出当独立来源。

### 9.6 运行预算与故障恢复

初始可配置预算：单用户同时 2 个研究 run，全局模型并发 4；一次默认研究最多 12 个外部工具调用，用户可手动继续深挖。该值是应用保护配置，不是 Tokendance 平台配额承诺。

临时超时、429、5xx 最多自动重试 2 次，指数退避并带随机抖动；遵守可用的 Retry-After。鉴权失败、额度不足、参数错误、权限拒绝不盲目重试。达到预算保留已完成结果并列剩余问题。

run 取消采用协作式取消：每次外部调用前后和发布前检查。已经发出的上游请求未必能立即停止，但取消后返回的内容不能再提交新版本。单次模型断流重试产生新 message_attempt_id，旧草稿标记中断，不把两次模型输出静默拼成一句话；它与 worker 的 active_attempt、用户手动创建的新 run 分开记录。

## 10 系统架构与代码组织

### 10.1 固定技术方案

前端 React＋TypeScript＋Vite，路由 React Router，服务端状态 TanStack Query，图表 ECharts。后端 Python＋FastAPI＋Pydantic，数据库 PostgreSQL，ORM/迁移 SQLAlchemy＋Alembic，向量扩展 pgvector，后台队列 Celery＋Redis，文件私有 OSS，同域反向代理 Caddy，Docker Compose 部署。

一个 Python 代码库分别启动 API 与 worker。两个后端分模块协作，不拆两套账户或互调 HTTP 的微服务。数据库、Redis 默认仅私网可达。

这里只定义未来目录，不代表当前已经创建应用代码。前端 fixture 只用于开发和自动化测试，必须标识，不用于冒充现场真实分析。

### 10.3 依赖隔离

A 提供 `CaseService / EvidenceService / RunService / PublicationService / ArtifactService`。B 通过授权接口读取和登记证据，返回 CandidateAnalysis，不直接更新 case 的当前版本指针。

公开企业资料缓存与私人 evidence storage 分区。共享公开缓存只存允许缓存的公开数据，不存用户目标、账号、合同或问答。私有检索先按 owner/case/availability 过滤，再做词法或向量匹配。

### 10.4 任务可靠投递

创建 run 与 outbox 记录在同一数据库事务中；后台投递器把 outbox 发送到 Celery，成功后标记。worker 通过 run 状态和唯一键实现重复消费安全。Redis 丢消息不能使数据库里 queued 的任务永久无人处理。

模型及解析任务不依赖浏览器连接存活。长任务保存阶段进度和可重用中间结果；重试只重做失效或失败阶段。部分解析失败必须记录页码和范围。

## 11 数据模型与字段契约

### 11.1 通用规则

- 主键 UUID；示例短 ID 不作为真实 ID 格式。
- 时间为 UTC ISO 8601，页面按 Asia/Shanghai 或用户设置显示；未知时间为 null。
- owner_id 从 session 注入，外部请求不得指定或改变。
- revision 为并发控制整数，version_id 为不可变内容版本 UUID，version_no 为用户可见序号。
- 数值使用 Decimal；金额或精确统计值在 JSON 中为字符串，并带单位和币种。
- 所有可删除内容有 availability 投影；正常版本追加与删除隐私内容分开处理。
- 建议 JSONB 存储类型化条款和 artifact spec，业务约束仍由 Pydantic 校验。

### 11.3 索引和数据库约束

case(owner_id, updated_at)、evidence(owner_id, case_id, availability)、observations(case_id, entity_id, metric_key)、claim_versions(claim_id)、run_events(run_id, seq)、runs(case_id, created_at) 建常用索引。assessment(case_id, version_no) 与 assessment(run_id) 唯一。工具请求中不能让模型自行决定租户过滤条件。

embedding 的实际维数在 Tokendance 探针后确定，不继承上一轮千问直连方案中的固定 1024 假设。切换 embedding 模型创建新 index 并重建；不得把不同模型向量混在一个近邻索引中。

### 11.4 产物和计算记录

artifact spec 描述固定渲染类型、列、坐标轴、单位、排序和空值说明。data 中每个值保存 observation_ids 或 calculation_id。calculation 保存 operation、input_ids、normalized_inputs、output、unit、formula_version。

允许算子初始为 select、filter、sort、group、sum、difference、ratio、period_change、compare。分母为零时返回 null 和原因；基期为负时同比变化须注明口径，不机械输出增长好坏。禁止执行任意 SQL、Python、JavaScript 字符串。

### 11.5 六类成果的最小联调契约

每个 artifact version 外层必须带 `schema_version / artifact_id / version_id / assessment_id / based_on_version / kind / title / status / spec / data / citation_index / calculation_index`。kind 是六类判别字段，spec/data 必须按对应 Pydantic 模型校验，禁止任意字典交前端猜测。citation_index 以 evidence_id 为键，值采用第 7.3 节完整引用；calculation_index 以 calculation_id 为键，值采用第 11.4 节记录。

通用 Datum：`value_type=text|decimal|date|boolean`；`value` 为相应值或 null；`value_status=available|missing|not_applicable`；`unit`、`currency`、`period` 默认 null；`missing_reason` 对 missing 必填，其他情况默认 null；`evidence_ids / observation_ids / calculation_ids` 默认空数组。decimal 的 value 必须为十进制字符串。系统生成的提问允许没有支持证据，但必须标 task_generated，不包装成已知事实。

单元格使用 cell_id，其他条目使用 item_id；同一 artifact 中跨版本的同一语义项沿用 ID，不以行序号作 ID。页面引用统一为 `{type:artifact_item, artifact_id, version_id, item_id}`，其中单元格 item_id 取 cell_id。后端按 version_id 读取历史，不跳到当前版本。所有以下示例仅为合成协议数据，不代表真实公司。

## 12 HTTP API 契约

### 12.1 共同规则

API 前缀固定 `/api/v1`。成功响应 `{data, request_id}`，分页追加 `page:{next_cursor,has_more}`；错误响应 `{error:{code,message,retryable,details},request_id}`。不把上游原始密钥、内部堆栈或私人提示词放入错误正文。

读接口使用会话 Cookie；写接口额外校验 Origin 和 `X-CSRF-Token`。`GET /auth/csrf` 允许匿名访问：没有会话时创建 30 分钟有效的匿名会话并返回绑定 token，注册/登录/找回密码使用该 token。登录成功轮换 session 和 CSRF，F 再获取新 token；匿名会话不能访问业务资源。创建与执行操作接受 `Idempotency-Key`。需要改变 case 内容的操作携带 `expected_input_revision`；版本不符返回 409，不默默覆盖。

受保护业务接口对未登录返回 401；注册、登录、找回/重置密码、CSRF 初始化、公开案例和公开健康接口不要求已登录，但保留各自的校验与限流。对象不存在或不属于当前用户时统一 404；已登录但被禁止的明确账号操作可返回 403。数据校验返回 422，文件超限 413，应用限流 429。用户界面显示可理解说明和 request_id。

### 12.4 文件上传示例

先创建 ingestion_batch，再调用 `POST /api/v1/cases/{id}/uploads`，请求 filename、mime_type、size_bytes、可选 client_sha256 和必填 batch_id。返回 upload_id、预留 document_id、短时 PUT URL、required_headers、expires_at。URL/粘贴文本也加入批次；单材料使用单成员批次。

上传地址绑定后端生成的单个 object_key，不允许客户端指定 bucket 或任意路径。完成后调用 `/complete`，请求 upload_id、batch_id、可选 claimed_entity_id 和 material_date。后端验证实际对象大小、文件签名与归属，并自行计算哈希；前端声明成功不能替代核验。

响应 202 返回 document_id、ingestion_run_id、processing_status 和 events_url。完成添加后 `/seal` 固定成员；解析终态见第 5.10 节，`/commit` 请求 included_document_version_ids、每份 included_pages、review_acknowledgements、expected_input_revision，返回 committed_revision、review_run_id；相同批次重复提交返回同一结果。全 ready 且 auto_commit=true 由服务端执行相同事务，否则等待用户确认。

文件读取通过 `/access` 获取同源 content_url、mime、size_bytes 和是否支持 Range；真实正文请求仍逐次鉴权，不返回可绕过删除权限的 OSS GET 签名地址。PUT 签名只允许写指定对象，不授予读权限；删除或取消后即使迟到上传成功，也不允许 complete 激活，并由清理任务删除残留对象。

## 13 A 和 B 的内部接口与 SSE

### 13.1 授权执行上下文

A 提供固定 owner/case 范围的 AnalysisContext，暴露 `evidence.search/get/register`、`documents.read`、`events.emit`、`cancellation.check`、`artifacts.stage` 等受控方法。B 不接收可自由切换用户的数据库连接或任意 SQL 工具。

B 实现 `execute_analysis(context, run_input) -> CandidateAnalysis`；可分阶段产出中间进度，最终必须返回明确 result_quality=`complete/partial` 和未完成事项。候选结构使用本项目 schema，不依赖 Tokendance 原生 JSON Schema 是否可用。

### 13.2 CandidateAnalysis

数组中的完整对象按第 7、11 章字段定义，实施时形成 Pydantic 嵌套模型，不能长期保留任意字典。未取得模型实际用量或价格时为 null，不填 0。A 的 publish 服务检查输入快照、引用、权限、取消状态、算术和展示结构，通过后才提交。

CandidateAnalysis.input_revision 指 run 的 base_input_revision；active_attempt 和 run_snapshot_id 必须与当前执行代次和最新快照一致。来源 staging、补搜后重建快照及发布时一次激活的唯一规则见第 8.1 节；初始和增量 run 都不能逐网页修改 case 输入，不能绕过发布事务。

### 13.3 结构化写回操作

operation.type 为 `add_candidate / propose_context_change / register_source / correct_observation / create_artifact / upsert_action`。每项带 operation_id、base_assessment_id、expected_input_revision、evidence_refs、payload、requires_confirmation。模型只能提议，服务端按当前用户请求和操作类型判断是否允许。

操作执行失败不返回“已经完成”。同 operation_id 重试不重复生成候选或清单。长期画像保存和删除通过专门业务接口及确认，不作为普通 Agent 自由工具。

需确认时，A 保存 operation 为 awaiting_confirmation，run 为 awaiting_user，发出 run.awaiting_user 事件。`/resolve` 请求 `{decision:approve|reject, answers, expected_input_revision}`；批准先进入 approved，经授权执行成功才进入 succeeded。拒绝进入 rejected，不改原条件；AI 可以继续提供不依赖该操作的解释。操作默认 30 分钟过期；输入基准变化时标 expired，返回 409，重新规划而不是把旧提议套到新任务。

`/resume` 仅接受 awaiting_user 且必需操作已解决的 run，携带 expected_input_revision 和 resolved_operation_ids。只补充转录确认且未改变分析基准的可续跑；已批准修改目标/材料等导致输入 revision 改变的，旧 run 标 superseded，响应返回新 run_id 基于更新后的输入继续。用户不会被要求手动复制整段对话重启任务。

### 13.4 SSE 协议

`GET /api/v1/runs/{id}/events` 使用同源会话 Cookie，不在 URL 中放 token。连接必须验证 run 归属。事件先持久化 PostgreSQL，再通过 Redis 通知在线连接；Redis 只负责加速。

业务事件格式：

```text
id: 13
event: run.stage
data: {"run_id":"run_003","seq":13,"stage":"comparing","message":"正在比较新增条款与已有材料","completed_units":2,"total_units":4}
```

固定事件类型：`run.snapshot / run.started / run.stage / run.awaiting_user / operation.updated / source.discovered / document.progress / evidence.ready / message.delta / message.completed / artifact.ready / assessment.published / run.warning / run.completed / run.failed / run.cancelled / run.superseded / content.withdrawn`。

- seq 在同一 run 中递增且唯一，事件携带 active_attempt；前端按 ID 去重并拒绝把旧代次事件作为当前进度。
- 首连返回 snapshot；重连按 Last-Event-ID 返回后续事件。页面重载后可用 `after_seq` 指定上次游标，该参数不包含秘密。
- 每约 15 秒发送注释心跳；心跳不入库。Cache-Control 为 no-store。
- 最终状态可重放，前端收到终态后关闭 EventSource。
- message.delta 是流式回答草稿，未完成前不作为已发布判断；引用完成校验后再变成可点击脚注。
- artifact.ready 和 assessment.published 只发送对象 ID、版本和摘要，不发送长效文件链接或私人原文。
- 浏览器断开不取消 run；用户取消调用单独 API。
- 如果上游不支持 token 流式，仍发送真实阶段事件；不能用延迟逐字显示冒充上游流式。
- 持久消息增量记录 source_refs；删除时同步脱敏并在重放时按当前可访问性再过滤。不能因事件是“历史记录”而绕过删除。

### 14.6 能力差异的处理

- 原生结构化输出不可用：普通文本生成 JSON → 本地校验 → 最多一次定向修复 → 失败则明确结构化失败，不写数据库。
- 原生 tools 不可用：后端固定工作流执行白名单工具，模型生成计划和解释，保留全部研究功能。
- 向量接口无权限：可使用经团队确认的本地嵌入模型；加载期间以中文分词＋关键词/BM25 检索，并标识降级。所有生成式模型请求仍走 Tokendance。
- OCR 或视觉某一路不可用：文本 PDF 本地提取；扫描件可走网关已授权版面解析或本地 OCR。图像整体理解与 OCR 文字识别分别验收，不能互相冒充。
- 网关搜索无权限：确认赛事允许的独立授权搜索服务并接入相同 SearchProvider；若不存在可用搜索渠道，标记该具体依赖未通过，不把只有用户 URL 的流程宣传成全网检索完成。
- 网页阅读不可用：对合法可访问页面使用 HTTP 抓取和正文提取，保留失败状态，不绕过登录、验证码或付费权限。

图片理解、真实检索和引用都属于交付验收项；降级路径用于解决能力差异，不用于掩盖未实现功能。

### 14.7 费用与错误

不继承上一版千问原价，也不承诺比赛的免费额度或 RPM。用量按实际返回记录，单价来自比赛配置或控制台；未知费用显示“未取得计价信息”。公开服务在本系统另设用户级调用预算。

供应商错误映射为应用层 `AUTH_FAILED / QUOTA_EXHAUSTED / RATE_LIMITED / MODEL_UNAVAILABLE / CAPABILITY_UNSUPPORTED / INVALID_REQUEST / UPSTREAM_TIMEOUT / UPSTREAM_FAILED / STREAM_INTERRUPTED / OUTPUT_VALIDATION_FAILED`。这是内部枚举，不假称 Tokendance 返回相同错误码。记录脱敏摘要与 request_id，保留可恢复阶段。

## 15 数据接入与真实案例

### 15.1 来源适配器统一返回

SourceResult 包含 source_id、source_type、title、url、publisher、asserter、published_at、event_at、retrieved_at、subject_identifiers、content_status、fetch_status、license_policy_id、raw_content_ref、warnings。

content_status 为 `snippet_only / full_text / partial_text / unavailable`。一个搜索命中先是线索，获取正文后才补充精确引用。正文来自另一平台转载时记录 canonical 来源；不能把摘要改写成原始发布机构的直接引文。

### 15.2 具体数据范围

| 来源类别 | 可用内容 | 实现方式 | 检查点 |
| --- | --- | --- | --- |
| 授权企业 API | 登记、变更、公开年报字段、部分处罚或执行信息 | ProviderAdapter 按实际采购/赛事权限调用 | 主体标识、时间、覆盖范围、缓存与展示授权 |
| 官方公告与披露 | 年报、财报、重大事项、公司说明 | 原网页或 PDF 获取，保留来源和页码 | 是否对应同一主体、期间和口径 |
| 企业官网 | 业务说明、招聘、服务与退款条款 | 搜索＋原文提取 | 企业自述与独立核实区分 |
| 公开报道 | 已发布的新闻或争议线索 | 有来源的搜索结果及正文 | 事件时间、是否转载、后续更正、是否同名公司 |
| 用户材料 | 合同、聊天、报价、付款和补充说明 | 上传解析与用户纠错 | 权限、完整性、原文位置、材料声明不等于认证 |

企业查询接口由 B 在 H0—H3 锁定实际可用服务，A 保存授权策略配置。网页公开可阅读不自动表示可以无限抓取或再分发。真实公示的部分字段可能未公开，页面按状态表达，不为填满表格制造数据。公开登记查询、风险记录和金融业务许可分开处理。[企业信息公示规则参考](https://www.samr.gov.cn/xyjgs/flfg/art/2024/art_be55c2e3a54a43e5ab12794c9dc87600.html)

### 15.3 文档解析步骤

1. 验证 MIME 与文件签名、大小、压缩包解压比例、页数及图片像素，拒绝可执行内容与宏执行。
2. 文本 PDF 优先使用文本层解析，DOCX 读取段落和表格；保留页级/段落级定位。
3. 扫描页和图片使用已验证 OCR/视觉路径，按页处理，保存失败页与质量说明。
4. 表格提取保留表头、单位、期间和合并单元格关联；财务数值进入规范化后再计算。
5. 分块保留标题、页码、上下文和主体信息；按语义段落切片，不固定截取全文前若干字符。
6. 先权限过滤，再混合关键词与向量检索；重排只影响排序，不改变原文。
7. 关键金额、名称、账号掩码和期限出现低确定度或冲突时，生成可纠正项。

定位只有页级时明确显示页级，不给不存在的高亮坐标。OCR 文本与图片说明的生成分别记录 parser 和 model 版本。

### 15.4 真实案例包要求

每个案例包保存 manifest：case_title、scenario、目标主体、用户意图是否为演示设定、sources、retrieved_at、材料授权范围、脱敏说明、初始证据集合、新增材料集合、预期变化、预期不变、预期未知。

演示材料真实性与用户意图真实性分开描述。可以用真实条款演示一个设定的购买意图；不把设定意图称为真实发生的付款。可以使用明确标注时间范围的历史公开资料回放；不能把当时快照包装成当前全量调查。

候选公开材料示例：Apple 官方在线销售条款和零售店政策包含不同渠道、产品及服务协议的适用条件。可在用户补充实际考虑渠道后，展示旧判断适用范围的变化；如果系统已经知道例外，则不能人为忽略来制造演示反转。[在线销售条款](https://www.apple.com.cn/shop/open/salespolicies)、[零售店政策](https://www.apple.com/legal/sales-support/sales-policies/retail_cn.html)

最终案例优先选团队有许可、可脱敏的真实合同及补件。真实公司不得搭配伪造的个人收款通知或负面聊天截图。自动化测试使用虚构主体的合成材料，与现场真实案例包分目录。

## 16 安全 隐私和公开部署

### 16.1 登录和访问

密码使用 Argon2 等成熟库实现安全哈希，不自写密码算法。Session 是高熵随机不透明 token，数据库只存哈希；Cookie 为 HttpOnly、Secure、SameSite=Lax，默认 24 小时有效，可由配置调整。登录和注册分别限速；同源 API、SSE 和前端减少跨域配置。

写请求验证 Origin 与 CSRF token。每次对象读取、下载、事件订阅、检索、导出都校验当前用户；UUID 难猜不是权限。模型不能提供可信的 owner_id。邮箱发送失败不能显示已送达。

### 16.2 文件和外部访问

OSS bucket 私有；PUT 上传地址短时有效，object_key 由后端生成。私人预览和导出通过本系统鉴权代理读取，每次请求核验 session、owner 与 availability；不发出绕过后端撤权的直接 GET 签名链接。代理流对删除信号尽力停止后续传输，但无法追回已经交付给客户端的字节。

URL 抓取限制 HTTP/HTTPS、域名解析和每次重定向，拒绝 localhost、内网、链路本地地址、云元数据地址和非允许端口，防止 SSRF。不向外部阅读器转发本系统 Cookie、用户登录凭据或非必要私有链接。

所有网页和文件内容属于数据，不是 Agent 指令。工具参数和调用权限由后端校验。Markdown 展示禁用不可信 HTML/脚本，外链安全打开；CSV 公式注入、文件名路径穿越和压缩炸弹纳入测试。

### 16.3 数据使用

在上传和设置中说明处理目的、保留期限、模型服务商与处理地区。公开演示默认脱敏姓名、电话、完整账户、身份证、签名等非必要信息。上传资料不自动用于模型训练或其他用户调查。

搜索关键词尽量只带公开主体、事项和公开标识；私人文件内容只按任务必要范围提供给经确认的模型服务。Tokendance 的数据保存、日志和处理地域以赛事协议为准，B 核实、A 配置说明；不能假设使用中转网关就不会发生数据保存或跨地域处理。

资料与历史记忆可选择停用、撤回和彻底删除。永久删除的处理按第 8.6 节执行。公开上线前核对本项目实际适用的服务、隐私和生成内容标识要求，不把接入某模型等同于整个应用已经完成所有运营手续。[个人信息保护法参考](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)

### 16.4 部署方式

先验证团队或主办方已有且适用于本项目的部署资源；没有现成资源时，可验证香港 ECS＋同区私有 OSS 的比赛部署方案。内地对外 Web 服务的备案等流程按实际情况处理，香港不等待内地 ICP 流程不等于免除其他义务。[阿里云备案条件](https://help.aliyun.com/zh/icp-filing/basic-icp-service/support/for-the-record-process-faq)

Compose 至少包含 web/proxy、api、worker、postgres、redis；文件持久化使用 OSS，数据库持久卷与加密备份。DB 和 Redis 不暴露公网。TLS 证书由受控域名与 Caddy 配置管理；实际验证 SSE 不被代理缓冲。

H3 前提供公网健康页；H10 前公网完成首次真实研究链路；H12 前接通私有上传与授权读取。每次演示排练从学校 Wi-Fi 和手机蜂窝网络各走一遍。保留本地同版本恢复环境和带采集时间的真实资料缓存，网络异常时明确说明缓存或本地运行，不冒充实时公网调用。

### 16.5 配置清单

部署使用以下类别的配置，不在本文填任何真实值：数据库与 Redis 地址、会话秘密、允许域名、OSS 区域和凭据、Tokendance 地址/Key/角色型号/能力配置、企业数据 Provider、搜索权限配置、邮件 SMTP、文件/任务限制、日志保留、备份和删除策略。
