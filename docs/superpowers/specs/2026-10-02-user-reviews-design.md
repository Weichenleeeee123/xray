# 用户评价设计

2026-10-02，围城拍板：做传统评价（星级 + 文字）；星级只显示分布，不算平均分；评价计入报告；含定性词的评价照发，加提示。

## 要守住的线

- 评价是"别人说的，未核实"，不是记录。它只能让人多留意，不能让人放心：好评再多也不标绿，差评最多到"要留意"，"有问题"留给官方记录。
- 星级不汇总成一个分数，报告里没有任何"总分"。
- 小企的越界检查不把评价原文当作"记录"：评价里写了"非法集资"，小企不能借它说出口。
- 不给真实公司预置评价。演示数据只给虚构的案例 C，标"演示数据"。
- 遮掉手机号、身份证号、住址再存。

## 数据

- 每家公司一个文件：`backend/data/reviews/<公司名哈希>.json`，git 忽略（`XRAY_REVIEWS_DIR` 可改，测试用临时目录）。
- 演示评价：`backend/data/fixtures/reviews.json`，只读，标 `demo: true`。
- 一条评价：`id`、`stars`（1–5）、`relation`（customer 客户 / employee 员工 / applicant 求职者 / other 其他）、`text`（10–500 字）、`nickname`（选填，≤20 字，空显示"匿名用户"）、`created_at`、`demo`、`author`（浏览器匿名编号的哈希，只存在评价文件里，不进案卷、不返回前端）。
- 没有账号。同一浏览器对同一家公司只能写一条（防手滑，不防刷，页面写明）。

## 接口

- `GET /api/reviews?company=&author=` → `{company, count, dist: {"5":n,…,"1":n}, reviews: [... , mine]}`，新的在前。
- `POST /api/reviews` `{company, stars, relation, text, nickname?, author}` → 同上。重复写 409。
- `POST /api/cases/{id}/reviews` → 把最新评价放进案卷，出新一版（trigger `reviews`，"更新用户评价"）。没有新评价 409。

## 计入报告

- 汇集数据时，有评价就记一条原始数据（source `user_reviews`，kind `user_review`）：标题"用户评价（N 条）"，内容是评价列表（不含 author），`as_of` 是最新一条的日期。评价没变，原始数据复用同一条。没有评价不记。
- 口碑信号加一条 `reputation.user_reviews`，标签"用户评价（未核实）"：
  - 少于 3 条：none，"评价太少，只作参考"。
  - 3 条以上且 1–2 星占一半以上：warn。
  - 其余：none，写条数和分布，不标绿。
- 前端把 none 的评价条目显示为"只作参考"，不算进"没查"。
- 一页结论（打印）不收评价条目：那一页写的是记录。
- 判断（judgments）不收评价条目：评价不是"记录里查到的"。
- 变化清单：评价条目照常逐条比对；只更新评价的那一版，开头写"这一版只放进了新写的用户评价：新增 k 条，现在共 n 条"。

## 前端

- 报告页标签栏最后加"评价 (N)"，N 是这家公司现在的评价条数。
- 面板从上到下：提示条（用户个人观点，未经核实，系统不判断真假）→ 5 到 1 星分布条 → "有 k 条新评价没进这一版 [放进报告]"（只在看最新版时）→ 写评价表单 → 评价列表（演示数据 / 你写的 标记）。
- 写完立即出现在列表里。

## 测试

存储（遮挡、重复、长度、演示数据只读）、接口、信号规则（0/2/3 条差评/全好评不变绿）、原始数据快照不含 author、刷新出新版和 409、小企越界检查不借评价放行、一页结论不收评价。
